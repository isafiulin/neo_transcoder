# NeoSRT

Сервис для Linux: передаёт UDP multicast MPEG-TS по SRT без перекодирования.
Управление — через веб-интерфейс на Flutter. Главная страница открывает список
SRT relay. Доступны клиенты, сессии, аудит и настройки учётных записей.
Кодер, профили кодирования, FFmpeg и FFprobe для работы сервиса не нужны.

## Переход с NeoTranscoder

Имя исполняемого файла и службы systemd остаётся `neotranscoder`, чтобы можно
было обновить существующую установку. Пути к конфигурации и данным сохраняются:

- `/etc/neotranscoder/config.json` — настройки сервера, SRT, хранения учётных записей и журналов.
- `/var/lib/neotranscoder/state.json` — пользователи и секрет подписи токенов авторизации.
- `/var/lib/neotranscoder/srt-state.json` — конфигурация relay и клиентов.
- `/var/lib/neotranscoder/srt-master.key` — существующий мастер-ключ SRT.
- `/var/log/neotranscoder/srt-audit/` — история аудита.

Существующие пользователи и ключи доступа SRT продолжают работать. Старые записи
кодера в `state.json` сохраняются как JSON для возможного отката, но не запускаются.
Раздел `ffmpeg` в старой конфигурации игнорируется. API кодера возвращает 404,
его экраны и менеджер заданий удалены. Удаление неработающего кодера само по себе
не уменьшает нагрузку CPU от активных SRT relay.

При обновлении служба перезапускается, поэтому текущие SRT-сессии прерываются.
Перед переходом сохраните резервную копию конфигурации, состояния и мастер-ключа
SRT. Процессами FFmpeg, запущенными отдельно от этой службы, нужно управлять отдельно.

## Установка и обновление через Git

На целевом Linux-сервере должны быть установлены:

- Git;
- Go — требования указаны в `go.mod`;
- Flutter — требования указаны в `ui/pubspec.yaml`;
- компилятор C;
- pkg-config и файлы разработки libsrt.

FFmpeg и FFprobe для работы сервиса не требуются. Пользователю, запускающему
развёртывание, нужен доступ к репозиторию и право установки через `sudo`.
Для закрытого репозитория используйте SSH-ключ доступа к Git; не включайте
пароли или токены в URL репозитория.

### Первая установка

Сначала изменения проекта должны быть закоммичены и отправлены в удалённый
репозиторий. Локальные неопубликованные изменения сервер не получит.

```sh
git clone git@github.com:isafiulin/neo_transcoder.git
cd neo_transcoder
```

Выберите существующую ветку или тег, содержащие новый скрипт развёртывания:

```sh
# Замените ИМЯ_ВЕТКИ_ИЛИ_ТЕГА на нужную ветку или тег релиза.
./scripts/deploy-git.sh git@github.com:isafiulin/neo_transcoder.git ИМЯ_ВЕТКИ_ИЛИ_ТЕГА
```

Скрипт выполняет следующие действия:

1. Получает указанную ревизию Git во временную папку.
2. Запускает тесты Go и веб-интерфейса.
3. Собирает веб-интерфейс и оба исполняемых файла для Linux.
4. Проверяет запуск собранных файлов.
5. Устанавливает новую службу либо обновляет существующую.

Тесты и сборка завершаются до изменения работающей службы. Ошибка на этих этапах
останавливает развёртывание. Сборка выполняется в отдельной папке и не затрагивает
локальные изменения в вашем checkout или рабочие данные сервиса.
Скрипт ничего не отправляет в Git.

При первой установке используется порт 8080. Откройте в браузере
`http://АДРЕС_СЕРВЕРА:8080`. Начальные данные входа — `admin` / `123456`;
после входа нужно сменить пароль. При обновлении существующие учётные записи сохраняются.

### Последующие обновления

Повторно запустите `deploy-git.sh`, указав нужную ветку или тег. Для установки
конкретной версии удобнее использовать тег релиза. Выбранная ревизия должна
содержать скрипты сборки и установки.

После обновления проверьте службу и диагностику:

```sh
systemctl status neotranscoder
sudo neotranscoder doctor
journalctl -u neotranscoder -n 100 --no-pager
```

Затем проверьте relay, активные сессии и аудит в веб-интерфейсе. Успешный
перезапуск systemd ещё не подтверждает доставку видео до получателя.

### Установка готового пакета на загруженный сервер

Сборка временно потребляет CPU и память. Если рабочий сервер уже перегружен,
соберите релиз на другой Linux-машине совместимой архитектуры, перенесите
каталог релиза на рабочий сервер и выполните:

```sh
# Замените /path/to/release на путь к перенесённому каталогу релиза.
sudo neotranscoder update --bundle /path/to/release
```

Обновление сохраняет предыдущие исполняемые файлы в
`/var/lib/neotranscoder/backups` и восстанавливает их, если команда перезапуска
службы завершилась ошибкой. Данные автоматически не откатываются.

Для новой ручной установки запустите из каталога релиза:

```sh
sudo ./install.sh --port 8080
```

## Разработка и сборка

Из корня проекта:

```sh
go test ./...
(cd ui && flutter analyze && flutter test)
./scripts/build-ui.sh
BUILD_UI=0 BUILD_SRT=1 ./scripts/build-release.sh
```

По умолчанию готовый пакет находится в `dist/neotranscoder`.
Веб-интерфейс встроен в Go-бинарник, поэтому после изменения интерфейса его
нужно пересобрать до сборки сервера.

Нативный SRT worker собирается на Linux с libsrt. Для сборки статического
Linux worker через Docker используйте `scripts/build-srt-worker-linux.sh`
и передайте путь к результату в переменной `SRT_WORKER` при сборке релиза.

Проверка сценариев Git-развёртывания без установки службы:

```sh
python3 scripts/test-deploy-git.py
```

Нативные проверки транспорта находятся в `scripts/test-srt-native.sh`
и `scripts/test-srt-caller-native.sh`. Эти диагностические скрипты используют
FFmpeg как тестовый источник или получатель; самому сервису он не требуется.

## Работа SRT relay

Сервис принимает существующий UDP multicast MPEG-TS и передаёт его по SRT,
не изменяя видео- и аудиопотоки:

```text
239.10.10.1:1234 UDP multicast MPEG-TS
  -> SRT worker NeoSRT
  -> Publish: SRT Caller -> IP:порт партнёра (партнёр — Listener)
  -> Accept: локальный SRT Listener <- один или несколько Callers партнёров
```

В режиме `publish` NeoSRT устанавливает одно исходящее соединение с IP-адресом
или доменным именем и UDP-портом партнёра. Получатель должен работать как
SRT Listener. В режиме `listener` NeoSRT слушает локальный UDP-порт,
а получатели подключаются к нему как Callers. Старые записи без поля
`direction` сохраняют режим `listener`.

Каждый relay работает в отдельном процессе. У каждой сессии есть ограниченная
очередь, поэтому медленный получатель не блокирует приём multicast. Менеджер
перезапускает завершившиеся с ошибкой процессы с ограниченной задержкой между
попытками; частые сбои обозначаются как `flapping`. Включённые relay запускаются
автоматически вместе с `neotranscoder.service`.

Если входные multicast-пакеты перестали поступать на заданное время, статус
становится `degraded`, а в аудит записывается событие `input_stalled`.
SRT-подключение остаётся открытым. После восстановления входа статус возвращается
в `running`, и записывается событие `input_restored`.

## Доступ клиентов и шифрование

Входящие подключения к Listener по умолчанию запрещены. При установлении
соединения проверяются:

- Stream ID — в строгом режиме это идентификатор настроенного клиента;
- исходный IP — должен входить в разрешённый список IP/CIDR клиента;
- состояние клиента и его назначение на этот relay;
- лимиты одновременных сессий клиента и relay;
- режим защиты: AES-256 с IP ACL либо только IP ACL.

AES-256 используется по умолчанию, в том числе для клиентов из старых версий.
Пароль SRT выводится из случайного локального мастер-ключа и версии ключа клиента.
Он не сохраняется в браузере или на диске в открытом виде. Интерфейс показывает
его один раз после создания клиента, смены ключа или перехода с незашифрованного
режима на AES-256. Смена ключа перезапускает назначенные работающие relay,
разрывает их текущие сессии и делает старый ключ недействительным.

Stream ID может быть обычным идентификатором клиента (`partner-a`) или строкой
SRT access control, например `#!::u=partner-a,m=request`.
Пример URL для получателя; замените `<one-time-key>` на выданный пароль SRT:

```text
srt://public.example.net:9000?mode=caller&transtype=live&streamid=partner-a&passphrase=<one-time-key>&pbkeylen=32
```

Для клиента в режиме `IP ACL only` параметры шифрования не нужны:

```text
srt://public.example.net:9000?mode=caller&transtype=live&streamid=partner-legacy
```

Откройте UDP-порт relay в межсетевом экране сервера и вышестоящей сети.
Если сервер за NAT, настройте перенаправление UDP-порта на адрес Listener.
В ACL указывайте исходный IP, который сервер видит после NAT.

Stream ID — идентификатор, а не секрет. В незашифрованном режиме другой
отправитель с того же разрешённого публичного IP может указать тот же Stream ID.
Поэтому предпочтительны выделенный IP партнёра и ограничения в межсетевом экране.
Для незашифрованных клиентов NeoSRT запрещает ACL `0.0.0.0/0` и `::/0`.
Ограничения общего потока нежелательных пакетов настраиваются в
nftables/firewalld или на сетевом оборудовании. Worker дополнительно
ограничивает частоту попыток подключения с одного IP, чтобы не переполнять аудит.

### Совместимость с VLC и получателями без Stream ID

Включите `allow_missing_stream_id` и явно выберите `default_client_id`.
Подключение без Stream ID проверяется только по этому клиенту: его состоянию,
назначению на relay, IP/CIDR ACL, лимиту сессий и ключу шифрования.
Сервис не выбирает клиента автоматически по пересекающимся ACL.

Выбранного клиента нельзя отключить, отвязать или удалить, пока режим
совместимости не выключен либо не выбран другой клиент по умолчанию.
Минимальный URL при AES-256:

```text
srt://public.example.net:9000?passphrase=<one-time-key>
```

Для клиента по умолчанию в режиме `IP ACL only` достаточно
`srt://public.example.net:9000`.

### Формат входного потока

Поддерживается MPEG-TS непосредственно в UDP multicast. Вход `rtp://`
отклоняется: пересылка заголовков RTP как части MPEG-TS повредила бы выходной поток.
Обработка RTP сейчас не реализована.

## Журналы и диагностика

Аудит SRT хранится отдельно от журнала приложения:

```text
/var/log/neotranscoder/srt-audit/srt-audit-YYYY-MM-DD.jsonl
```

Он содержит попытки подключения и причины отказов, удалённые IP и порты,
Stream ID, клиента, relay, версию SRT удалённой стороны, состояние шифрования,
подключения и отключения сессий, итоговую статистику, пропадание и восстановление
multicast, ошибки worker и изменения конфигурации оператором.

Файлы создаются с правами `0600`, синхронизируются с диском при добавлении,
ротируются ежедневно и удаляются по сроку хранения — по умолчанию через 90 дней.
Интерфейс получает метрики и события сессий через SSE. Экран Audit поддерживает
фильтры по relay, клиенту и типу события.

Просмотр журналов на сервере:

```sh
journalctl -u neotranscoder -f
tail -f /var/log/neotranscoder/neotranscoder.log
tail -f /var/log/neotranscoder/srt-audit/srt-audit-$(date +%F).jsonl
```

Первые два журнала содержат события службы, stderr worker, ошибки запуска
и диагностику сервиса. Аудит SRT помогает определить, кто подключался, почему
ему отказали, когда сессия завершилась и когда пропал или восстановился вход.
Таймаут отсутствия входа задаётся через `input_timeout_seconds` — по умолчанию
10 секунд. По истечении таймаута relay становится `degraded`, но Listener
продолжает работать.

## API

Маршруты с авторизацией: `/api/srt/relays`, `/api/srt/clients`,
`/api/srt/sessions`, `/api/srt/audit`, `/api/events`, `/api/system`,
`/api/doctor` и `/api/users`. Вход и управление токенами — `/api/auth/*`.
`GET /api/health` возвращает идентификатор сервиса `neosrt`.

Актуальный пример конфигурации — `config.example.json`. Для доступа к веб-панели
используйте доверенную сеть либо обратный прокси с TLS.
